# HomePulse Frontend-Backend Integration Report

## Executive Summary
This report analyzes the integration between the HomePulse frontend (React Native/Expo) and backend (Pure TS Engine, SQLite, Zustand) modules. The overall architecture is sound, following a store-driven reactive pattern. However, several alignment gaps have been identified that could lead to inconsistencies or fragile behavior as the project grows.

## Findings

### 1. Inconsistent Action State Data
**Issue:** `app/result/action-state.tsx` manually recreates `ActionState` metadata using a helper function `getActionStateData`.
**Impact:** This bypasses the descriptive data (labels, explanations, recheck intervals) generated by the clinical engine. If engine rules change, the UI will become out of sync.
**Recommendation:** Components should consume the full `ActionState` object provided in the `TriageOutput`.

### 2. Proactive Database Initialization
**Issue:** The root `_layout.tsx` does not proactively initialize the SQLite database.
**Impact:** Initialization is currently lazy-loaded by stores. This can cause a slight delay or race condition when the first screen (usually `Home`) attempts to load data.
**Recommendation:** Call `getDb()` or an explicit `init()` function in `app/_layout.tsx` within the `useEffect` block.

### 3. Type & Label Alignment
**Issue:** Discrepancies exist between engine-generated labels and frontend-coded labels.
**Impact:** Confusing UX if different terms are used for the same triage state (e.g., "Monitor" vs "Monitor at Home").
**Recommendation:** Centralize action state labels and metadata within the engine's rule configuration and ensure the frontend strictly renders these values.

### 4. UI Error & Loading States
**Issue:** Not all screens fully leverage the `loading` and `error` properties exposed by the Zustand stores.
**Impact:** Users may experience "ghost" UI states or unhandled failures during database operations.
**Recommendation:** Implement a consistent "Screen Wrapper" or "State View" component that automatically handles store-level loading and error states.

### 5. Sync Queue Visibility
**Issue:** The sync queue (`sync_queue` table) operates entirely in the background without UI feedback.
**Impact:** Users have no way of knowing if their shared caregiver links have actually synced with Supabase.
**Recommendation:** Add a subtle indicator (e.g., a "Syncing..." spinner or a "Cloud Up to Date" checkmark) in the `Settings` or `Home` screen.

## Recommended Next Steps
1. **Refactor `ActionStateScreen`:** Update it to use the full `triage_output` payload.
2. **Update Root Layout:** Add proactive database initialization.
3. **Audit Component Error Handling:** Ensure all store-interacting screens handle `loading` and `error` states.
4. **Enhance `NetworkBanner`:** Extend it to show sync status in addition to raw connectivity.
